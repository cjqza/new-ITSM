# 第2轮接口文档 v2.0：转人工、客服队列、受理与技术分析

## 1. 团队老大结论

根据产品经理 Agent 对 Java 第一版的评估，第 2 轮将人工处理链路前半段固化为接口：用户主动转人工、客服查询队列、客服受理、客服提交技术分析。Python Agent 继续只提供摘要和建议，不直接修改工单核心状态。

## 2. 接口清单

| 接口编号 | 接口名称 | 方法 | 路径 | 所属服务 |
|---|---|---|---|---|
| ITSM-R2-001 | 用户主动转人工 | POST | `/api/v1/user/tickets/{ticketId}/handoff` | itsm Java 主服务 |
| ITSM-R2-002 | 客服查询待处理队列 | GET | `/api/v1/support/tickets/queue` | itsm Java 主服务 |
| ITSM-R2-003 | 客服受理工单 | POST | `/api/v1/support/tickets/{ticketId}/accept` | itsm Java 主服务 |
| ITSM-R2-004 | 客服提交技术分析 | POST | `/api/v1/support/tickets/{ticketId}/analysis` | itsm Java 主服务 |

## 3. 客服侧请求头

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| X-Tenant-Id | String | 是 | 租户 ID |
| X-Operator-Id | String | 是 | 客服或技术人员 ID |
| X-Role | String | 是 | `SUPPORT_AGENT`、`TECH_EXPERT` 或 `ADMIN` |

## 4. 状态机规则

- 用户主动转人工：`AGENT_ANSWERED` -> `PENDING_HUMAN`。
- 客服受理：`PENDING_HUMAN` 或 `REOPENED` -> `ACCEPTED`。
- 技术分析：`ACCEPTED` 或 `TECH_ANALYSIS` -> `TECH_ANALYSIS`。
- 非法状态必须返回 `ILLEGAL_TICKET_STATUS`。

## 5. 权限与租户隔离

- 用户只能对本人、本租户工单主动转人工。
- 客服队列只能返回本租户内 `PENDING_HUMAN`、`REOPENED`、`ACCEPTED`、`TECH_ANALYSIS`、`IN_SUPPORT` 工单。
- 非客服角色不能访问客服端接口。

## 6. 前端 Agent 任务

- 根据接口文档设计“转人工”按钮、客服待办队列、受理按钮、技术分析表单。
- 只能使用本文档字段，不得新增状态或错误码。

## 7. 后端 Agent 任务

- 实现转人工、队列、受理、技术分析接口。
- 保证所有接口受租户、角色和状态机约束。
- 继续沿用 Java 主系统作为工单事实源。

## 8. 测试 Agent 必测场景

- 用户主动转人工成功。
- 客服查询队列只看到本租户工单。
- 客服受理成功。
- 技术分析成功。
- 非客服角色访问客服端接口被拒绝。
- 未受理工单直接技术分析应失败。

## 9. 验收标准

- 第 2 轮接口均已在 Java Controller 和 Service 中落地。
- 测试用例覆盖人工队列和状态机。
- 分析师评分大于等于 85。
